# MALULEKE-KS — BUSINESS RULES DOCUMENT v1.0

**Derives from:** PLATFORM-CONSTITUTION-v1.md (structure) and PLATFORM-OVERVIEW-AND-RATIONALE.md (rationale)
**Status:** Locked
**Scope:** This document is behavior. The constitution defines what entities and routes exist; this defines what happens — the explicit policy every implementation must enforce, not just describe.

---

## 1. Content Publishing Rules

| Rule | Statement |
|---|---|
| BR-1.1 | `contentStatus` transitions `draft → published` are blocked at the API layer — not just discouraged in the admin UI — whenever `clientVisibility != PUBLIC` and `clientApproved = false`. This is a server-side constraint, never a client-side checkbox someone forgets |
| BR-1.2 | `clientVisibility` defaults to `REQUIRES_APPROVAL` at creation time for any `System` linked to an `Organization` where `isClient = true`. The default is restrictive; opening it up is a deliberate admin action, never the starting state |
| BR-1.3 | `NDA_RESTRICTED` systems never expose `repoUrl` or `liveUrl` in any public API response, regardless of `contentStatus`. This is enforced at the serialization layer, so a future new endpoint can't accidentally leak it |
| BR-1.4 | `ANONYMIZED_ONLY` systems never expose the linked `Organization` name publicly. Case study text must refer to it generically ("a fintech client") unless `nameDisclosureApproved` specifically authorizes the real name. This is a deliberately separate flag from `clientApproved` (BR-1.1) — a client approving *publication* of an anonymized case study is not the same authorization as approving *disclosure of their real name* in it. Reusing `clientApproved` for both would make masking unreachable for any actually-published system, since BR-1.1 already requires `clientApproved=true` to publish anything non-`PUBLIC` The organization list and the catalog's organization filter follow the same rule: an organization appears (and can be filtered by) only through a published system that discloses its name — otherwise the list itself would name the client. |
| BR-1.5 | `contentStatus` stays a fixed three-value state machine — `draft` / `published` / `archived` — not a lookup table. Per the EXT-1 exception already established for `ClientVisibility`: this is a control state, not a growing content dimension |
| BR-1.6 | The GitHub sync is the source of the catalog: a system it creates from a repo in the owner's **own** homes is **shown by default** — published with the status *On GitHub* and flagged `needsCuration` so the admin sees it as new and can hide, feature or curate it. Which repos are shown by default is the setting `github.sync.newRepoVisibility` (public and private / public only / hidden — **public only** to start, the owner's choice for the live site; private repos wait in the admin for review). A repo in a **client organisation** (BR-1.2) or one the owner only **collaborates** on (BR-1.11) always lands hidden until approved — the database refuses to publish those regardless (BR-1.1, BR-1.11). Uncurated systems are never counted in the homepage ledger. A live system whose public repo is gone from GitHub (deleted, or no longer in the owner's homes) is hidden by the next sync and flagged for curation — never deleted (BR-1.9), and only on GitHub's own "not found" for a repo in an account that was listed in full that run. *(Replaced 2026-10-01 at the owner's direction: "they shall be there by default, and I choose which to hide" — the earlier rule kept every synced repo as a hidden draft until curated.)* |
| BR-1.7 | Every system comes from GitHub, private repositories included — the owner's work isn't limited to public repos. Synced repos, public or private, follow BR-1.6 — shown by default per the setting, and the admin decides what stays hidden. A private repository is never linked publicly: the public view says it is private (`repoPrivate`) and offers access on request instead of a repo URL. *(Replaces the earlier rule that private repos were never synced — owner direction, 2026-09-19.)* |
| BR-1.8 | `needsCuration` is cleared (`false`) the moment an admin opens and saves that system's detail view in `/admin/systems/[id]` — whether or not they choose to publish it. A system an admin has actually looked at no longer belongs in the curation queue, even if it stays in draft |
| BR-1.9 | `System` rows are never hard-deleted. Retirement is expressed as `contentStatus = archived`. There is no `DELETE /admin/systems/{id}` endpoint |
| BR-1.10 | A request that would set `contentStatus = published` is evaluated and committed inside a single database transaction that re-reads `clientVisibility` and `clientApproved` at commit time — never against a value read earlier in the request — so two concurrent edits can't race past the BR-1.1 check |
| BR-1.11 | A system's repo is either the owner's own or one the owner collaborated on (a lookup — `RepoRelationship` — so new kinds need no code change). Where the relationship requires it, the repo owner's permission is asked first, and the system is published only once that permission is recorded as granted, with who gave it. Changing a relationship so that it requires permission is refused while a published system uses it without one. Enforced by the database |
| BR-1.12 | A journey entry about a system is public only while that system is published — an entry can never reveal a system the visitor can't see (the same principle as BR-6.2). When a system first ships, the database drafts a journey entry for it; the admin edits and approves it, nothing is published automatically |
| BR-1.13 | Any content — a system, journey entry, achievement, role or education entry — can be scheduled: it is published with a future publish time and becomes public exactly at that time, on its own, with no job to run. Scheduling *is* publishing, so every publish rule (BR-1.1, BR-1.11, …) is checked when the schedule is set, never skipped until later. Until its time, scheduled content is invisible everywhere a visitor can look — pages, search, skill evidence, the CV — and so is anything shown only through it (e.g. a scheduled system's journey entries). A publish time on unpublished content is refused, and one is dropped when content stops being published |
| BR-1.14 | A system's link never breaks when it's renamed. Every slug a system gives up — renamed by the admin or following a GitHub repo rename — permanently redirects to its current slug, and stays reserved for that system: no other system can take it (that would hijack the old links), though the same system may take it back. A redirect is answered only for a system the visitor can see |
| BR-1.15 | Every version of a system's case study and description is kept — who wrote it and when — and can never be edited or deleted. Any earlier version can be restored; the restore is recorded as a new version, so history only grows. The platform's own writing is never lost to an overwrite |
| BR-1.16 | Content that describes the owner now — systems, roles, education, the profile — records when a person last really touched it: an edit to something a visitor sees, or an explicit "reviewed, still accurate". Automatic updates (the GitHub sync) never count. Live content untouched for the admin-set number of days (default 90) is surfaced to the owner, oldest first. Journey entries and achievements are dated events and never go stale |
| BR-1.17 | The owner's photos are data, uploaded in the admin — one current per place on the site (e.g. the About portrait). An upload is accepted only if it decodes as an image; it is re-encoded and stripped of every piece of hidden metadata (location, camera) before it is stored. A version is superseded, never altered or deleted — only its description for screen readers can change — and an earlier one can be made current again |
| BR-1.18 | Every system's screenshot is data: captured from its live site automatically (the daily job takes new sites, sites whose address changed, and captures older than `screenshots.refreshDays`, at most `screenshots.maxPerRun` a day) or uploaded by the owner in the admin. The owner's upload wins — no automatic capture replaces it until the owner chooses *Back to automatic*; the database refuses otherwise. Every image is accepted only if it decodes as an image, and is re-encoded with all hidden metadata stripped. Versions are superseded, never altered or deleted. A screenshot is shown only for a live system, never for NDA work (BR-1.3) |

## 2. Inquiry Handling Rules

| Rule | Statement |
|---|---|
| BR-2.1 | *(Replaced 2026-10-02 by Let's Talk, LETS-TALK-SPEC LT-6 — the four-state flow couldn't hold a hiring conversation.)* Every `Inquiry` starts at `NEW`, and `NEW → REVIEWED` is the only way out of `NEW` — every message is triaged before anything else. From review: `NEEDS_INFO`, `RESPONDED` (shown "In discussion"), `ACCEPTED`, `DECLINED`, `ON_HOLD`, `CLOSED` or `WITHDRAWN`; decisions and closures can be **reopened** to `REVIEWED`. The allowed moves are a database trigger; every change is appended to `InquiryStatusChange` by the database itself (append-only), with a private reason kept apart from what the applicant was told (LT-7). A change made from a stale screen is refused (version check). Nothing is decided automatically (LT-11) |
| BR-2.2 | Triage SLA: every `new` inquiry gets reviewed within 48 hours. This is the one part of the platform where the solo-maintainer cadence (Constitution §11) is deliberately tighter than the monthly content pass — a job or client opportunity doesn't wait a month |
| BR-2.3 | Required fields: name, valid email format, message (minimum 20 characters — long enough to filter empty/spam submissions; maximum 5,000 characters — long enough for any legitimate detailed request, short enough to close off an unbounded-payload submission vector), `inquiryType` |
| BR-2.4 | Rate limit: maximum 5 inquiry submissions per IP per 24 hours by default — both numbers are admin-editable platform settings (`inquiry.rateLimit.maxPerWindow`, `inquiry.rateLimit.windowHours`), bounded so the limit can be tuned but never switched off. Applies identically whether the submission came through the human form or the agent's `submit_inquiry` tool — no privileged path around the limit. The IP address used for this check is retained only as long as needed to enforce the 24-hour window — it is not part of the 24-month `Inquiry`/`Event` retention policy (BR-5.2) and is purged on its own short rolling schedule |
| BR-2.5 | `source` is captured automatically from the referring page/system at submission time — never a field the visitor fills in — so attribution (Constitution §8) is always accurate. When no `Referer` header is present (direct navigation, privacy-conscious browsers), `source` is recorded as `"direct"` rather than left to fail or crash the submission |
| BR-2.6 | `POST /inquiries` accepts an optional client-generated idempotency key, bound to the message it was first used for: the same key with the same payload within 10 minutes returns the original confirmation (double-click, retry on a flaky network); the same key with a different payload is refused (`409`) — a key can't be reused to fish for another submission's confirmation *(strengthened 2026-10-02)* |
| BR-2.7 | The contact form's honeypot field, if filled, returns the same `201` confirmation shape as a real success — never a `400` or any response distinguishable from a genuine submission — so an automated filler gets no signal that it was caught. No `Inquiry` row is created |
| BR-2.8 | A submission must carry a signed form token from `GET /inquiries/form`, at least `inquiry.minFillSeconds` old and at most 12 hours old. Missing, forged or too-fast tokens get the honeypot's treatment (BR-2.7: the same `201`, nothing stored); an expired one asks the visitor to refresh *(added 2026-10-02, Let's Talk)* |
| BR-2.9 | Besides the per-connection limit (BR-2.4), one email address can send at most `inquiry.rateLimit.perEmailPerDay` messages in 24 hours, and receive at most `notifications.recipientDailyCap` automatic emails — the form can't be used to flood an inbox *(added 2026-10-02)* |
| BR-2.10 | Let's Talk (docs/LETS-TALK-SPEC.md, LT-1…LT-14): each category asks only its own questions, validated on the server; compensation is an explicit choice; meetings are events with their own time zone; documents are PDFs checked by their bytes, never public; the reference identifies and never authorises; notes and applicant messages never share a table; email goes through an outbox and never undoes state *(added 2026-10-02)* |

## 3. Admin Access & Security Rules

| Rule | Statement |
|---|---|
| BR-3.1 | Two-factor authentication is mandatory before any write action succeeds. There is no "remind me later" or degraded-but-functional state — a session without verified 2FA cannot mutate data |
| BR-3.2 | Five consecutive failed logins lock the account temporarily; each further lockout without a successful login in between doubles the next one (up to a day), and a successful login resets it — so failures never buy a fresh set of guesses on a fixed schedule. A failed login answers exactly as an unknown email does, revealing nothing about which email is the admin's. *(Reworded 2026-09-30, #91: "progressive delay" described no enforceable behaviour; the rule now states the escalation that is enforced and tested.)* |
| BR-3.3 | Admin sessions expire after 30 minutes of inactivity, full stop |
| BR-3.4 | Every admin mutation — and every login attempt, success or failure — writes to `ActivityLog` automatically at the middleware layer. No code path is permitted to bypass this; it is not something a route handler opts into |
| BR-3.5 | A login `challengeToken` (issued after step-1 credentials succeed) expires after 5 minutes and is single-use — consumed on the first `verify-2fa` attempt, success or failure. An expired or already-consumed token returns the same generic `401` as a wrong code, and the admin must restart from credentials |
| BR-3.6 | The 6-digit TOTP code is rate-limited independently of BR-3.2: 5 consecutive failed verification attempts against the same `challengeToken` invalidate that token immediately (BR-3.5) rather than allowing continued guessing — a stolen or guessed `challengeToken` cannot be brute-forced into a session |
| BR-3.7 | In addition to the 30-minute idle timeout (BR-3.3), every admin session has a hard maximum lifetime of 12 hours from issuance, regardless of activity. A session that hits either limit is ended identically — redirect to `/admin/login`, neutral "Session ended" copy, no distinction shown between idle-expiry and absolute-expiry |
| BR-3.8 | The session identifier issued after step-1 credentials (if any pre-2FA state is tracked) is never the same identifier promoted to an authenticated session after step-2 succeeds. A new session ID is always minted at the moment 2FA verification succeeds, preventing session-fixation across the two-step flow |
| BR-3.9 | Every state-changing admin request (`POST`/`PATCH`/`DELETE` under `/admin`) is protected against cross-site request forgery — the session cookie is `SameSite=Strict` at minimum, and mutating routes verify a CSRF token or an equivalent double-submit / origin check before executing |
| BR-3.10 | `AdminUser.email` is normalized to lowercase on write and on every lookup (login, password reset). Uniqueness and authentication can never be bypassed or fail solely due to letter-casing differences |

## 3a. Account Recovery

| Rule | Statement |
|---|---|
| BR-3.11 | At 2FA setup, exactly 10 recovery codes are generated, shown once, and stored hashed. Each is single-use, consumed on successful use (already reflected in `AdminUser.recoveryCodes` being an array of one-time codes) |
| BR-3.12 | When fewer than 3 unused recovery codes remain, the admin dashboard surfaces a persistent (non-blocking) notice to regenerate a fresh batch. Regenerating invalidates all previously issued codes immediately |
| BR-3.13 | Because `AdminUser` is single-owner (Constitution §1), there is no self-serve "forgot password" email flow in V1 — that would require a second communication channel the platform can't yet verify safely. Recovery from total lockout (password and all recovery codes lost) is a documented manual operator procedure (direct database credential reset by whoever holds infrastructure access), not an application feature. This is a deliberate, accepted V1 limitation, not an oversight |
| BR-3.14 | Every authenticator (TOTP) code is single-use. Once a code is accepted — at login or at any other step that asks for one — neither it nor any code from an earlier 30-second step is accepted again, so a code seen over a shoulder or in a log can't be replayed within its validity window. The check and the recording of the used step are one atomic database statement |
| BR-3.15 | The admin can change their own password while signed in. It requires the current password **and** a live TOTP code (BR-3.14); the new password must differ from the current one. A successful change ends every session issued before it (the caller receives a fresh one). Failed attempts are counted per session, and the fifth ends that session — a stolen session can't be used to keep guessing, and the owner is never locked out of signing in again. Every attempt, success or failure, is logged (BR-3.4) |

## 4. AI and Agent Boundaries

| Rule | Statement |
|---|---|
| BR-4.1 | Tier 2 agent tools are read-only with exactly one exception: `submit_inquiry`. No other tool may ever mutate `System`, `Timeline`, `Skill`, `Testimonial`, or any other entity. *(2026-09-30: the AI guide goes further — it only drafts an inquiry for the visitor to review and send through the normal form; it never submits one itself. PUBLIC-REDESIGN-PLAN §3a.)* |
| BR-4.2 | `submit_inquiry` invoked by the agent passes through the identical validation and rate-limiting as the human form (BR-2.3, BR-2.4). The agent gets no privileged bypass |
| BR-4.3 | The concierge must not state a fact about Kurhula that isn't grounded in the site's public data — the public views it is given whole, or `ContentChunk` retrieval once that corpus outgrows `concierge.contextBudgetTokens`. When asked something ungrounded, the correct behavior is to say it doesn't know and point to the contact form — never to infer or fabricate a plausible-sounding answer, and never to make a commitment (rates, availability, dates) on his behalf. *(Replaced 2026-09-30: whole-corpus grounding for a small corpus, PUBLIC-REDESIGN-PLAN §3a.)* |
| BR-4.4 | New agent tools ship disabled via `Flag` by default. Enabling a tool is an explicit admin action — opt-in, never opt-out |
| BR-4.5 | A system's description and case study are **written automatically by AI from its public repository** (README, file layout, dependency files, workflows, commits) and go live without a code change or an approval step — always labelled as written by AI, with when. The evidence is the only source: no claim the repository doesn't back, no personal details (emails, phone and ID numbers are also stripped after generation), never from a private repo or from client work without approval. They are rewritten only after the repo changes, at most every `writeups.refreshDays`, at most `writeups.maxPerRun` per day, and only while `writeups.enabled` is on (BR-4.4). **The owner's own words are never replaced**: saving an edit makes that field the owner's, and the database refuses a generated write over it; handing it back to the AI is an explicit admin act ("Regenerate from repo", or clearing the case study). Every version is kept (BR-1.15). Anything else the AI produces — replies, flagged discrepancies — still only drafts. *(Replaced 2026-10-01 at the owner's direction: "every system description and case study should be generated automatically … using their repo" — the earlier rule required approval of every generated case study.)* |
| BR-4.6 | Nothing a visitor sends changes what the concierge is or may do. The route accepts only a whitelisted request (user text, and the guide's own answers and tool parts — never a system message, file or unknown tool), bounded by the `concierge.*` settings; the instructions treat every visitor message as conversation, never as instructions, whoever it claims to come from; the concierge never reveals its instructions. Adversarial evals (`tests/ai-evals`) must pass before a change to the prompt, grounding or tools ships |

## 5. Analytics and Privacy Rules

| Rule | Statement |
|---|---|
| BR-5.1 | No `Event` is recorded before consent is given via the cookie/consent banner. Consent gates collection, not just display |
| BR-5.2 | `Inquiry` and `Event` records are retained for 24 months from creation, then anonymized (PII stripped, aggregate data retained) or purged. One retention policy governs both, per the Constitution's stated requirement that they share a policy. This runs as a scheduled job (same scheduler adapter as the GitHub sync — `lib/adapters/scheduler/`), not a manual process |
| BR-5.3 | A number presented publicly as a statistic or achievement ("By the numbers" — Constitution §8) is shown only as an admin-approved value: the platform proposes values from public data, the admin approves or rejects each one, and the history of values is kept. Nothing about visitors — raw, live or per-visitor analytics — is ever public. Live counts of the owner's own catalog (systems shipped / in progress / queued on the homepage) are facts about the content, not statistics, and follow the admin's status changes directly. *(Clarified 2026-09-19: the owner asked for finished systems to move into the shipped count as soon as they're marked done.)* |
| BR-5.4 | BR-5.1's consent gate applies equally to the first-party `Event` table and to any third-party analytics provider (Vercel Analytics) — a visitor declining consent is excluded from both, not just the first-party one |
| BR-5.5 | A visitor may request deletion of a specific `Inquiry` they submitted. In V1 this is handled manually — the confirmation screen and email (BR-2.6-adjacent) states "To request removal of this submission, contact [email]" — and the admin actions it by hand via `/admin/inquiries`. A self-serve deletion endpoint is deferred to V1.1 (Constitution §13); this rule exists so the right itself is honored from launch, even before the automated path exists |

| Rule | Statement |

## 7. CV and Document Generation Rules

| Rule | Statement |
|---|---|
| BR-7.1 | Visitors are offered up to two CVs, each clearly labelled and never passed off as the other: the **generated CV**, built from the live database at the moment it's requested, never a stale copy; and the **uploaded CV**, the owner's own file exactly as uploaded, always shown with its upload date. *(Replaced 2026-09-30, #92: the rule used to forbid any manually maintained file. The owner wants their own CV offered too, so the rule now keeps each option honest instead of forbidding one.)* |
| BR-7.2 | Prior documents are superseded, never deleted: a generated document when a new one is generated for the same `type`/`targetRole`/`format` (PDF or Word), and an uploaded CV when a new file of the same format is uploaded. An uploaded version's content can never be altered, and an earlier version can be made current again. Consistent with the platform's additive-only philosophy (EXT-1) |
| BR-7.3 | The CV carries only what the site itself shows: published roles, education, projects and certifications, with every BR-1.x masking applied, plus the owner's profile. It never invents content — a missing fact is reported by the completeness check for the owner to supply, and a suggested summary is drafted only from facts already on the CV and saved only if the owner accepts it |
| BR-7.4 | The CV is generated ATS-safe, identically as PDF and Word: one column, standard section headings, real text in reading order (no tables, columns or images carrying content), no hyphenation, and every link written out as text. A target role may reorder projects, bullets and skills by relevance; it never rewrites or drops the owner's words |
| BR-7.5 | The admin decides which CV options visitors see and which is listed first. At least one option is always visible, the first one is always a visible one, and the generated CV can't be hidden until an uploaded CV exists — a visitor is never left without a CV. A hidden option is refused everywhere (listing, on-screen view, generating, downloading), not merely left out of a list |
| BR-7.6 | An uploaded CV is accepted only if its content really is a PDF or a macro-free Word (.docx) document — its name and declared type are never trusted — and it is within the admin-set size limit (never above what the platform can receive). It is always served as a download (an attachment, with content sniffing off), never rendered inline, and downloads are rate-limited |

## 8. Extension Governance

| Rule | Statement |
|---|---|
| BR-8.1 | New values may be added to any lookup table (`Status`, `Domain`, `InquiryType`, `MilestoneType`, `SkillCategory`) by the admin at any time, without a deployment |
| BR-8.2 | An existing lookup value that's in use is never hard-deleted — it's soft-deprecated (marked inactive, hidden from new-entry pickers) so historical records referencing it stay accurate. Hard deletion is reserved for values that were never actually used. This is enforced in code (`lib/rules/lookups.ts` checks for referencing rows before allowing a delete), not left to admin discipline alone |
| BR-8.3 | A lookup value's `key` stays unique (including deprecated ones) — an admin cannot create a new value with the same `key` as a soft-deprecated one. The correct action is reactivating the deprecated value, and the API returns a specific, actionable error (`LOOKUP_KEY_DEPRECATED`) rather than a raw uniqueness-constraint failure |

---

*Every rule above is enforceable at the API or middleware layer — none of them depend on an admin remembering to follow a convention. That's the difference between a business rule and a suggestion.*
